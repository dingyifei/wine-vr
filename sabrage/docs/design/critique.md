VERDICT:
Not plannable as-is, but close — and the blockers are decision-shaped, not research-shaped. The three designs are individually strong and mutually corroborating on the hard pipeline facts (privilege boundary, byte-parity artifacts, write-once toml policy, guard/permanent mutation split, telemetry unit traps), and Design 3's honest-stub phasing already defuses the worst v1 scope risks. What prevents handing this to an implementer is that the designs disagree on the load-bearing spine — the parity mechanism (contract/-restructure vs grep-lib.sh tests are mutually exclusive, with different commit #1s), the workspace/CLI layout, the IPC/check-ID vocabulary, and the phase order — and four pipeline realities have no owner in any design: app-quit semantics for a live session (where Design 1's kill_on_drop spec is actively wrong), per-game streaming overrides that cannot work against a global read-once toml, the legacy protocol=oxrsys launch branch, and the first-run repo_root onboarding that the not-run-from-the-repo .app absolutely requires. One reconciliation ADR pass that picks the parity mechanism, one layout, one event vocabulary, and one sequence, plus explicit answers to those four unowned facts (and the small-contradictions bundle), turns this into a directly implementable plan.

STRENGTHS:
- The hard pipeline invariants are covered somewhere in the set, usually redundantly and consistently: byte-identical shared artifacts (host manifest with trailing newline, toml template, cxbottle.conf exact line, steam_appid.txt without trailing newline, .sha256 marker), the single sudo boundary implemented via osascript with skip-when-current-bytes, TCC App Management detection with the Settings deep-link and Terminal fallback, exec-path process matching replacing pkill -f, the two distinct wineserver budgets (5s fatal / 4s soft), helper self-heal as an AutoFix, adb forward --remove per-serial (never --remove-all) vs reverse --remove-all asymmetry, and WINEDEBUG caller-precedence.
- Design 1's single check registry with LaunchPolicy (NotGating/Block/WarnOnly/AutoFix) is the right abstraction: it operationalizes CLAUDE.md's 'every launch-critical requirement gets a doctor section AND a run preflight' rule as one table, and correctly encodes every documented doctor-vs-run divergence (protocol=oxrsys Fail-vs-Warn, graphics backend Fail-vs-autofix, host manifest content-vs-presence).
- Design 2's rejection of demo.sh→sabrage delegation is thoroughly argued and correct for the stated goal (independent failure domains, a harness that tests something real, fresh-clone bootstrap); its divergence-detection matrix genuinely answers 'what catches an edit to only lib.sh' (the fingerprint tripwire), and the volatile-check flags show real operational thinking.
- Design 3 is unusually implementation-ready on Tauri specifics: Channel-vs-global-event split, the Edit-menu-or-no-clipboard macOS trap, single-instance ordering, minimal capability file because all fs/process work lives behind commands, titleBarStyle Overlay with drag-region guidance, and the honest-stub policy ('never fake data' — labeled placeholders for charts until telemetry lands) which defuses the biggest v1 scope trap.
- Crash-recovery via persisted guard state (session_state.json written before the audio mutation, reconciliation banner on next launch, Stop that can actually restore audio after kill -9) appears in Designs 1 and 3 and is the single clearest genuine improvement over demo.sh, correctly identified as such.
- The telemetry plan handles the nasty documented details: GRAPH-seconds vs STATS-milliseconds converted once in Rust, runtime_status.json liveness judged by updated_at_unix_ms staleness never file existence, rotation/inode-aware tailing, tail-from-end for the unbounded session_log, the standby-freeze heuristic (state==5 + stale enc1s + fresh battery), and it correctly defers every UNVERIFIED surface (8082 routes, toml key names beyond the six, runtime_status state enum) instead of building on them.
- Nothing in any design breaks the existing demo.sh flow or repo conventions by accident: logs stay in gitignored logs/ with compatible naming, evidence/ untouched, app state lives under ~/Library/Application Support/Sabrage/ not OXRSys/, and Design 2's shell edits are the only demo.sh changes — deliberate, sequenced first, and verified by output byte-diff.

=== GAP 1: Parity architecture (Designs 1 vs 2 vs 3 — mutually exclusive)
ISSUE: The three designs ship three incompatible parity mechanisms. Design 2 restructures the shell itself: new top-level contract/ dir, generated scripts/demo/contract.gen.sh sourced by lib.sh, setup.sh/install.sh switched to read shared template files, chk() slug instrumentation of every doctor row, '# preflight:' tags in run.sh — all as zsh-first Phase 0 commits. Designs 1 and 3 leave the shell untouched and make lib.sh the parse-target of Rust tests (Design 1's parity.rs asserts the toml template equals setup.sh's heredoc — a heredoc Design 2 deletes; Design 3's pins.rs greps lib.sh for constants Design 2 moves out of lib.sh). The check-ID vocabularies also differ (Design 1 'doctor.09b.helper-arm64' vs Design 2 'build.helper-arm64'), and Design 2 mandates its slugs land as commit #1 before any Rust exists.
WHY: This is the spine of the whole project — the user's core requirement is 'keep demo.sh alive without doubling maintenance pain.' Whichever mechanism is chosen determines commit #1, what CLAUDE.md's 'lib.sh is the single source of truth' line becomes, what the parity tests assert, and what the CheckId type in sabrage-core is named. Implementing Design 1's grep-tests and then adopting Design 2's contract restructure throws the tests away; implementing both simultaneously is contradictory.
SUGGESTION: Make this the first ADR. Recommended resolution: adopt Design 2's contract split as the end state (it is the only one where templates-as-shared-files make byte drift structurally impossible), sequence it exactly as Design 2 Phase 0 (behavior-neutral zsh commits verified by byte-diffing doctor output and a no-op install against the live root-owned manifest), adopt Design 2's slug scheme as THE CheckId vocabulary used by Design 1's registry and Design 3's DoctorEvent, and drop Design 1's grep-lib.sh tests in favor of the contract regen check plus the fingerprint tripwire. If the up-front shell risk is deemed too high, explicitly defer contract/ to a later phase and ship Design 1's grep-tests as a documented interim — but write that decision down; do not let both coexist in the plan.

=== GAP 2: Run lifecycle / Tauri exit semantics (no design owns it; Design 1's spec is actively wrong)
ISSUE: No design specifies what happens to a live Beat Saber session when Sabrage quits (Cmd-Q, window close, logout, crash). Design 1 specs .kill_on_drop(true) plus process_group(0) on spawn_streamed — applied to the wine launch child, app exit would SIGKILL the CrossOver wine wrapper mid-session (while wineserver and the game survive detached), which is neither clean teardown nor clean detach, and contradicts its own 'the wine launch is never SIGKILLed' rule. Neither design mentions Tauri's RunEvent::ExitRequested / api.prevent_exit(), which is the only way to run the async INT-path teardown (wineserver -k, bounded wait, dashboard kill, audio restore — multi-second work) before macOS tears the process down. The inventory explicitly says a GUI must treat app-quit and window-close as TERM-equivalents.
WHY: This is the most likely real-world failure: user quits the app while streaming, Mac audio is left routed to BlackHole at 100% (silent speakers), dashboard orphaned, and the half-killed wine wrapper produces exactly the stale-wineserver hang the pipeline documents. The session_state.json reconciliation banner only fixes it on the NEXT launch.
SUGGESTION: Specify the exit policy explicitly: intercept ExitRequested; if a session is live, show a three-way dialog (Stop session and quit / Keep session running and quit / Cancel). 'Keep running' requires kill_on_drop(false) on the wine spawn specifically and relies on session_state.json + runtime_status.json for reattach/reconcile on next launch; 'Stop and quit' runs the INT teardown with a small progress window before allowing exit. Also specify whether Stop can operate on a session Sabrage did not start (stop.sh semantics say yes — bottle-scoped, needs only the bottle name).

=== GAP 3: Edit-game per-game streaming overrides (screen map + Design 3) vs the runtime config model
ISSUE: The screen map's Edit-game card offers per-game bitrate/codec/encoder/res-scale/refresh overrides with 'overrides live in the game entry only; the runtime toml stays global.' But all five knobs exist ONLY in the global oxrsys-runtime.toml, read once at alvr_initialize — there is no env var, flag, or per-launch channel for any of them. Design 3's hand-wave ('applied at launch time where demo.sh parity allows, i.e. env/flags') references a mechanism that does not exist. As specified, the override sliders are dead controls; the only way to honor them is rewriting the global toml before each launch, which collides with the write-once/edit-in-place policy, races demo.sh, and violates Design 2's rule that every GUI action stays expressible as a demo.sh command line.
WHY: A settings surface that silently does nothing is worse than absent — it poisons trust in every other control, and this project has exactly one game anyway (Beat Saber 1.29.4 is a hard pin), making per-game overrides doubly speculative.
SUGGESTION: Drop the per-game streaming override card from v1: show the global streaming values read-only with a lock icon and an 'Edit global settings' link. If per-game is ever truly wanted, spec it explicitly as toml-rewrite-before-launch with backup/restore and a PARITY.md entry, and put that to the user as a decision — never as an implicit design assumption.

=== GAP 4: Workspace / crate / file layout (three-way conflict, plus a verified gitignore error)
ISSUE: Layout disagreements that hit the very first commits: frontend at sabrage/ui/ (D1) vs sabrage/src/ (D3); sabrage-cli as its own crate (D1, 'separate binary recommended') vs a bin target inside sabrage-core (D3); D2 adds sabrage-contract-gen and sabrage-parity crates no other design has; the Tauri crate is 'sabrage-app' in D1/D2 and unnamed in D3. Gitignore additions also disagree, and D3's entry 'sabrage/src-tauri/target/' is wrong for a workspace rooted at sabrage/Cargo.toml — cargo puts the shared target at sabrage/target/ (verified: the current .gitignore has no target/ rule at all, so an unignored workspace target dir would dump gigabytes of build output into git status).
WHY: These are the files created on day one; three divergent layouts mean guaranteed rework and broken relative paths in parity tests (D3's pins.rs test hardcodes ../../scripts/demo/lib.sh, which shifts if the crate moves).
SUGGESTION: One layout ADR before scaffolding: sabrage/{Cargo.toml (workspace), Cargo.lock (tracked), crates/sabrage-core, crates/sabrage-cli, src-tauri (sabrage-app), plus D2's two crates if the contract mechanism is adopted}; pick ONE frontend dir; gitignore additions: sabrage/target/, sabrage/node_modules/, sabrage/dist/, sabrage/src-tauri/gen/. Note the existing blanket *.log and *.dylib rules already cover stray artifacts.

=== GAP 5: IPC / event vocabulary (Design 1 vs Design 3 type systems)
ISSUE: Design 1 defines one global Event enum (snake_case, tag="type", emitted app-wide on 'sabrage://event', mirrored to events.jsonl) with CheckOutcome/FixId-string types. Design 3 defines per-operation tauri::ipc::Channel streams with different payloads (StageEvent/DoctorEvent, camelCase, tag="kind"), a FixAction Rust enum instead of FixId strings, and only two global events (session://status, doctor://badge). These shape sabrage-core's entire public API and the TS mirror, and Design 2's live differ additionally requires the check-ID field to be its slug vocabulary.
WHY: The event types are the contract between core, CLI, harness, and frontend — building core against one shape and the frontend against the other forces a rewrite at integration time, and the events.jsonl greppability promise (D1) evaporates if the shipped types are D3's.
SUGGESTION: Unify before Phase 1: adopt Design 3's transport model (Channels per operation + the two global broadcasts — the correct Tauri 2 idiom, auto-cleanup, no cross-screen leakage) carrying Design 1's richer payload content (run_id, StepId strings, CheckOutcome with detail/duration, structured ErrorPayload with fix id), with check ids = Design 2's slugs. Keep events.jsonl as a core-side sink written regardless of transport. Pick FixAction-as-enum with a stable serde string form so it serves both the UI and the slug-keyed PARITY.md.

=== GAP 6: Run stage completeness — legacy protocol=oxrsys launch branch
ISSUE: run.sh, when protocol=oxrsys, warns and takes a materially different tail: no audio routing, no dashboard, adb reverse --remove-all then reverse tunnels for tcp:9944/9945/9946/9948, then 'am start' of the legacy Android client. No design's run implementation mentions this branch — the Settings screens grey out audio/dashboard toggles for oxrsys, but what Launch actually does under that protocol is unspecified everywhere.
WHY: All three designs claim run.sh parity; silently dropping a whole branch is precisely the undocumented drift the parity harness exists to prevent, and a user who flips the protocol seg control in Settings gets undefined behavior from the Launch button.
SUGGESTION: Make an explicit v1 decision: either implement the legacy tail (it is small — four adb reverse calls plus one am start, all already inventoried) or hard-block Launch when protocol=oxrsys with a clear 'legacy USB path — use ./demo.sh run' message, recorded as a PARITY.md divergence. Do not leave it implicit.

=== GAP 7: First-run onboarding — locating the wine-vr checkout
ISSUE: The .app is not run from the repo, yet the screen map has no screen and Design 3's phases have no step for acquiring repo_root. Design 1 specs it as a persisted setting ('prompted-for in the .app') but no design defines the prompt, validation, or what happens before it is set. This machine is live proof of the stakes: multiple sibling checkouts exist and the root-owned host manifest currently points at a deleted one (27-beta-4). Design 3's single-instance plugin also implicitly binds one app to one repo_root with no stated switching story.
WHY: Every command in the app depends on repo_root; without an onboarding flow the .app's first launch dead-ends, and a wrong or moved root reproduces the exact silent no-VR failure mode the pipeline already documents (stale absolute dylib path in the host manifest).
SUGGESTION: Add a first-run gate + Settings 'Repository' card: folder picker validated by presence of demo.sh and scripts/demo/lib.sh, stored in settings.json; changing it marks install state stale and deep-links the privileged manifest rewrite; the card always shows which checkout the host manifest's library_path currently points at (parsed, like doctor 12) so multi-worktree confusion is visible instead of silent.

=== GAP 8: Parity ops resilience — pre-push hook and constructed PATH vs documented toolchain loss
ISSUE: Design 2's committed pre-push hook runs cargo test on every push; the user's own memory documents the brew toolchain vanishing repeatedly and rustup living off-PATH in non-login shells (verified by Design 3's probe: no rustup in a non-login shell), plus a nix profile (/run/current-system/sw/bin) supplying adb. A missing cargo would hard-block ALL pushes, including zsh-only fixes and submodule pointer bumps — the worst moment for the escape hatch to be needed. Separately, Design 1's constructed child PATH hardcodes brew/cargo/android dirs and omits the nix profile dir entirely.
WHY: A parity gate that fails-closed on toolchain absence will get disabled permanently the first time it misfires, defeating the mechanism; a PATH that misses the nix dir makes tools visible in Terminal invisible to the .app, producing 'all toolchain checks FAIL' doctor noise.
SUGGESTION: The hook must degrade gracefully: if cargo/rustup are absent, print a loud warning and pass (the fingerprint test will catch drift at the next healthy cargo test run); keep PARITY_SKIP=1. For PATH, derive it once from the login shell (zsh -lc 'echo $PATH', cached in settings with a refresh button) instead of a hardcoded list — this also future-proofs against the machine's brew/nix mix.

=== GAP 9: Phase sequencing (Designs 1, 2, 3 prescribe three incompatible orders)
ISSUE: Design 1: core first (paths/consts/parity → doctor → … → telemetry), Tauri shell LAST. Design 3: Tauri walking skeleton FIRST (Phase 0), then core. Design 2: zsh instrumentation commits before ANY Rust. Each order is defensible; as written they contradict each other on what the first three commits are.
WHY: An implementation plan needs one ordered backlog; three orders mean the planner (or agent) picks arbitrarily mid-flight, and Design 2's Phase 0 in particular cannot be retrofitted cheaply after Rust parity tests exist against un-instrumented shell.
SUGGESTION: Merge into one sequence and state it once: (1) Design 2 Phase 0 shell instrumentation IF the contract ADR adopts it (it must come first or never); (2) Design 3 Phase 0 walking skeleton in parallel (touches nothing shared); (3) then Design 1's core order (doctor first, read-only, immediately parity-testable) inside Design 3's phase structure. Explicitly mark which phases can proceed concurrently.

=== GAP 10: Goldberg per-file sub-flags (Edit-game Patches card) fight demo.sh idempotency
ISSUE: The screen map gives the Goldberg toggle 'per-file sub-flags' over the steam_settings markers (offline.txt, disable_networking.txt, disable_overlay.txt), but run.sh unconditionally truncate-creates all three on every launch — as will any parity-faithful Sabrage run port. A user who unchecks one would see it silently reassert on the next launch from either front-end.
WHY: Another dead-or-lying control, and a concrete two-front-ends-thrash scenario of the kind Design 2's whole architecture exists to prevent — but in app-state territory its harness does not cover.
SUGGESTION: V1: render the three markers read-only ('applied at every launch'), keep only Goldberg on/off status plus the Revert action (.orig-steam restore — itself new functionality all designs correctly propose). Per-flag configurability only if/when the launch port makes them honest inputs, with the documented caveat that demo.sh will re-add them.

=== GAP 11: Small contradictions and unsourced UI data (bundle — resolve in one pass)
ISSUE: (a) Log filename: D1 uses demo.sh's exact name with a '-2' collision suffix; D3 always appends '-sabrage' — different artifacts, pick one. (b) D3's minimumSystemVersion '14.0' vs the pipeline's hard macOS 27 doctor gate. (c) D3 mandates a persistent self-signed cert for TCC stability while the stated user constraint says ad-hoc is acceptable and D1 leaves it open — all three agree only that it needs an early empirical test. (d) Session footer 'WiFi band' has no data source anywhere in the inventory (session.json gives current_ip; nothing reports band). (e) The mockup files Sabrage.dc.html/styles.css are not in the repo (verified) — no design states where they are copied from. (f) Doctor 13b/16b silence-when-clean: D1's Rust renders green rows while D2's zsh tap emits 'skipped' — the Tier-2 differ will report mismatches unless this mapping is declared. (g) App-support store layout differs (D1: settings/library/session-state/runs split vs D3: one state.json) — the crash-recovery file needs independent atomic writes, favoring D1's split. (h) D1 lets doctor run concurrently with mutating stages; doctor cmp-ing overlay files mid-install produces flickering spurious FAILs.
WHY: Individually minor, but each is a fork an implementing agent will hit and resolve inconsistently; (c) in particular gates the project's founding motivation (the one-time App Management TCC grant) and needs a decision plus a Phase-2 empirical test against a built bundle, not a dev binary.
SUGGESTION: Resolve all eight in the reconciliation ADR: recommend D1's log naming (interchangeability was the stated goal), minimumSystemVersion aligned with reality or documented as advisory, an early spike that builds a bundle twice under both signing options and verifies the TCC grant persists, dropping 'WiFi band' from the footer (show transport instead), naming the mockup source location (it lives outside the repo per the video/script git-excluded convention — say so), a declared skipped≙pass-when-clean mapping in the differ, D1's store split, and doctor deferring (or annotating) rows while a mutating stage holds the operation lock.
